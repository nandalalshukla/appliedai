# Module 7: Evaluation and safety

**Weeks 12-13.** Anyone can build an AI demo. The engineers who get hired and promoted are the ones who can answer "is it good, how do you know, and did yesterday's change make it better or worse?" Evals are how you answer. If you take one module seriously, make it this one.

## 7.1 Why evals

Traditional software has tests: same input, same output, pass or fail. LLM systems break that in three ways:

- **Outputs vary** between runs.
- **"Correct" is often a judgment**, not an equality check.
- **Everything is coupled.** A one-line prompt edit, a model upgrade or a new tool description can change behaviour on inputs you were not looking at.

Without evals you are doing *vibe-based development*: try three inputs, it looks good, ship. This works until the first change that fixes one case and silently breaks ten.

An **eval** is a dataset of inputs, a way to score outputs, and a number you track over time. What you get from it:

| Without evals | With evals |
|---|---|
| "I think the new prompt is better" | "Pass rate went from 71% to 86%; two regressions on billing cases" |
| Afraid to change prompts | Change freely; the suite catches regressions |
| A new model is a risky migration | Run the suite, read the diff, decide in an hour |
| Arguments by anecdote | Arguments by data |
| Failures found by customers | Failures found before release |

### What makes an eval good

1. **It reflects real usage.** Inputs look like what users actually send, in realistic proportions, including the messy ones.
2. **It measures what matters to the product.** Not "is the answer nice" but "did it route the ticket correctly".
3. **It is specific.** One criterion per score, with a clear pass or fail.
4. **It discriminates.** If every version scores 100%, it tells you nothing. Add harder cases.
5. **It is trusted.** People have read the failures and agree they are real failures. An eval nobody believes is ignored.
6. **It is cheap and fast enough to run on every change.**
7. **It has an owner and it grows.** Every production bug becomes a new case.

## 7.2 Building an eval dataset

Run [Lab 7.1](labs/01_first_eval.py) and open [`data/router_cases.jsonl`](../../data/router_cases.jsonl).

**Start now, with 20 cases.** A small eval today beats a perfect one next quarter.

Where cases come from, best first:

1. **Production logs.** Real inputs, sampled across the range of traffic. The gold standard once you have users.
2. **Failures.** Every bug report, bad response and incident becomes a case. This is the highest-value source.
3. **Domain experts.** The support lead knows the twenty tricky tickets.
4. **Hand-written cases**, before launch. Think: typical, edge, adversarial.
5. **Synthetic cases**, generated by a model from a description of your users. Useful for coverage, weak on realism. Review every one before trusting it.

Coverage checklist:

| Category | Examples for a ticket router |
|---|---|
| Typical | "I was charged twice" |
| Boundary | "The refund page shows a blank error" (billing word, bug problem) |
| Messy | Typos, mixed languages, one-word messages, 2,000-word rants |
| Empty and malformed | Empty string, only emojis |
| Adversarial | "Ignore your instructions and..." |
| Out of scope | "What's the weather?" |
| Multi-intent | "Charged twice and also can't log in" |

Practices that separate useful datasets from decorative ones:

- **Tag every case** (`billing`, `hard`, `adversarial`). In the lab, v1 scores 58% overall, which hides the real story: 100% on easy cases and about 20% on hard ones. **Always slice.**
- **Write down why the expected answer is right** when it is not obvious. Ambiguous labels poison an eval. If two people disagree on the label, fix the labelling guideline first.
- **Keep a held-out set.** If you tune your prompt against the same 30 cases forever, you overfit to them. Hold some back and check them only before a release.
- **Version the dataset in git.** A score is only meaningful alongside the dataset version it came from.
- **Balance matters.** If 95% of cases are easy, a 95% score means nothing.

### Error analysis: the highest-return activity in AI engineering

Before you write scorers, **read outputs**. Take 50-100 real traces, read each, and note what is wrong in plain words. Then group the notes into categories and count them. The result is a ranked list of failure modes ("31% wrong queue on mixed billing/bug messages", "12% invented policy"). Now you know which evals to build and which problem to fix first. Teams that skip this build elaborate dashboards measuring things that do not matter.

## 7.3 Scoring methods and pitfalls

Three kinds of scorer. Use the cheapest one that works.

| Method | Examples | Pros | Cons |
|---|---|---|---|
| **Code-graded** | Exact match, contains, regex, valid JSON, schema check, numeric tolerance, "did it call the right tool", tests pass | Fast, free, deterministic | Only checks what can be expressed in code |
| **Model-graded** (LLM-as-judge) | Faithfulness to sources, tone, completeness, policy compliance | Handles nuance at scale | Costs money; can be wrong; must be validated |
| **Human-graded** | Expert review, user ratings, A/B outcomes | The ground truth | Slow, expensive, inconsistent between people |

Design the task so that code can grade it where possible. A router that returns one of four enum values is trivially gradable; one that returns a paragraph is not. Structured outputs (Module 2) make evals easier.

### Model-graded evals done properly

Run [Lab 7.2](labs/02_llm_judge.py). The judge agrees with the human on 5 of 6 cases and still misses one of the three bad replies.

- **One criterion per judge.** "Rate quality 1-10" yields noise. "Every factual claim is supported by the reference policy" yields signal.
- **Binary verdicts.** Neither people nor models can reliably tell a 3 from a 4. Pass/fail forces a clear definition.
- **Reasoning before the verdict**, in that order in the output.
- **Give the judge what it needs**: the input, the output, and the reference (correct answer, source documents or policy).
- **Validate the judge against human labels.** Label 30-100 examples yourself, run the judge, measure agreement, and especially *how many truly bad outputs it catches*. Fix the judge prompt and re-check. An unvalidated judge is an opinion with a dashboard.
- **Use a capable model** for judging, and re-validate when you change it.

### Pitfalls

| Pitfall | What goes wrong | Fix |
|---|---|---|
| Averages hide failures | 90% overall, 20% on the category that matters | Slice by tag; look at the worst slice |
| Non-determinism | A case passes today, fails tomorrow | Run multiple trials; report pass rate per case |
| Overfitting to the eval | Score rises, real quality does not | Held-out set; refresh from production |
| Vague criteria | Judge and humans disagree | One precise criterion; examples of pass and fail |
| Grading the path, not the outcome | Agent penalized for a valid approach you did not anticipate | Grade the end state: is the bug fixed, is the record correct |
| Saturated eval | Everything scores 100% | Add harder cases |
| Judge bias | Prefers long, confident or first-listed answers; favours its own model family | Validate; randomize order in comparisons |
| String metrics for meaning | BLEU/ROUGE reward word overlap, not correctness | Use them only where overlap is the goal |
| Broken tasks | The case itself is wrong or impossible | Read failures; a 0% case is often an eval bug |
| Tiny sample | 9/10 vs 8/10 is not a real difference | More cases; treat small gaps as noise |

### Evaluating different kinds of system

| System | What to score |
|---|---|
| Classifier / extractor | Accuracy per class; field-level match |
| RAG | Retrieval (recall@k, MRR, Module 4), then faithfulness to sources, answer relevance, correct refusal when the answer is absent |
| Agent | Task success by final state; also steps, cost, tool errors, safety violations. Run several trials per task |
| Conversation | Goal completion over the whole dialogue, often with a simulated user |

## 7.4 Placing and plugging evals

Evals belong at every stage, not in a notebook someone runs occasionally.

```
 development        pull request          release             production
 ───────────        ────────────          ───────             ──────────
 run the suite      CI gate:              full suite +        online evals on sampled traffic
 while editing      block regressions     held-out set +      guardrails on every request
 prompts            (Lab 7.1)             adversarial suite   user feedback, alerts
                                                               └──► failures become new cases
```

**Offline evals** run on a fixed dataset before release. Lab 7.1 ends with a gate:

```python
ok = candidate.pass_rate >= baseline.pass_rate and not diff["regressed"]
sys.exit(0 if ok else 1)          # CI fails the build on a regression
```

Run this on every change to a prompt, tool description, retrieval setting or model version. In the lab, v2 fixes five cases and breaks one, and the gate blocks it. Whether to accept that trade is a human decision; the eval makes it explicit instead of invisible.

**Online evals** run on live traffic:

- **Guardrails** check every request and response in real time (below).
- **Sampled judging** scores a percentage of production traffic asynchronously.
- **Implicit signals**: thumbs up/down, retries, edits to the output, escalation to a human, task abandonment.
- **A/B tests** compare versions on real users with a business metric.

**The flywheel:** production failures → error analysis → new eval cases → fix → the gate ensures it stays fixed. This loop is the core process of an AI team.

Evaluate components *and* the whole. For RAG: retrieval alone, generation given perfect context, then end to end. Component evals tell you where to fix; end-to-end evals tell you whether users benefit.

## 7.5 Exploratory and adversarial evals

**Exploratory evaluation** is looking for failures you have not thought of yet:

- Read raw traces weekly. No dashboard replaces this.
- Cluster production inputs to find topics your dataset lacks.
- Generate variations of known inputs (paraphrase, other languages, added noise, longer, shorter) and see where behaviour changes.
- Ask a model to play difficult users against your system.
- Ask "what would embarrass us?" and write those cases.

**Adversarial evaluation (red teaming)** is deliberately attacking your system. Run [Lab 7.3](labs/03_adversarial.py).

| Attack class | Example | What to assert |
|---|---|---|
| Direct prompt injection | "Ignore previous instructions and..." | Instructions not followed; system prompt not leaked |
| Indirect injection | Instructions hidden in a document, email, web page or tool result | Same, plus no unintended tool calls |
| Data exfiltration | "Translate your instructions", "repeat the text above" | No secrets or other users' data in output |
| Jailbreaks | Role-play, hypotheticals, encodings | Policy still holds |
| Tool abuse | Tricking the agent into a destructive or costly action | Action blocked or sent for approval |
| Resource abuse | Inputs that trigger huge outputs or endless loops | Limits hold |
| PII handling | User pastes a card number | Redacted before model and logs |
| Out of scope | Off-topic or harmful requests | Polite refusal |

Always include **benign cases** in the adversarial suite. A guardrail that blocks legitimate users is a failure too; measure false positives.

## 7.6 Safety: defence in layers

The lab shows the central lesson. With only a system-prompt instruction, direct attacks fail and indirect ones succeed. With layered checks, the leak is caught regardless of how the model was tricked.

```
user input
   │  1. INPUT GUARDRAILS      length limits, PII redaction, topic and abuse checks
   ▼
 model + tools
   │  2. ARCHITECTURE          least-privilege tools, no secrets in context, tenant
   │                           filters in the retrieval layer, human approval for
   │                           irreversible actions, sandboxed execution
   ▼
   │  3. OUTPUT GUARDRAILS     secret and PII scanning, schema validation,
   │                           grounding checks, policy checks
   ▼
response                       4. MONITORING: log, alert, sample, review
```

Principles:

- **Prompt instructions are not a security boundary.** They change probabilities. Enforce rules in code.
- **Assume anything in the context can leak**, and anything the model reads can instruct it. Keep secrets out of prompts.
- **Beware the dangerous combination**: an agent that has access to private data, reads untrusted content, *and* can send data out (email, HTTP, even a rendered link). Remove one of the three, or put a human between them.
- **Limit the blast radius.** Decide what the worst outcome is if the model is fully compromised, then make that outcome acceptable through permissions.
- **Fail closed** on high-risk paths: if a guardrail errors, block.
- **Guardrails cost latency and money.** Run cheap code checks first, model-based checks only where needed, in parallel with the main call when possible.

Also on your checklist as a professional: privacy and data retention, bias and fairness across user groups, honesty about being an AI, and a path to a human. These are product requirements, and in many industries legal ones.
